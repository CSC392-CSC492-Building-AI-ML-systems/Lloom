## 2. Design decisions

Defaults chosen so work can start. Change any of them in review.

1. **Location.** The backend goes in a new `lloom_api/` folder, next to `lloom_web/`. It is its own Python project and installs `text_lloom` with `pip install -e ../text_lloom`.
2. **Storage.** Everything goes in one SQLite file, through the stdlib `sqlite3` module, with no ORM. That covers projects, datasets, runs and jobs. Uploaded files and session pickles are stored as BLOB columns, not as files on disk, so there are no paths to manage and nothing to clean up. The DB path comes from `LLOOM_DB_PATH` (default `lloom_api/lloom.db`, gitignored).
3. **Sessions.** A run's `lloom` object is saved with `get_pkl_str()` after every job and loaded before the next one. Models are never stored with the session. They are rebuilt from the current settings each time a session is loaded. Two reasons:
   - Models hold API clients, which can't be pickled.
   - An `AsyncOpenAI` client shouldn't be reused across separate `asyncio.run` calls.
4. **Jobs.** *(edited)* A run is one job: generate, then score every concept (flow (a), matching the frontend's progress page).
   - A single-worker `ThreadPoolExecutor` runs each job with `asyncio.run(...)` in its own thread, which keeps clustering off the event loop.
   - Job status and progress are written to SQLite. *(edited)* The progress page polls `GET /runs/{id}`, which includes the run's latest job as `latestJob`, because the page's URL only has the run ID. `GET /jobs/{id}` returns the same job object.
   - A job still running at server startup gets marked `Failed`, so the UI doesn't poll forever.
   - A run can be cancelled. The cancel takes effect at the next progress callback, between steps (B6).
   - One worker means one job at a time (open question 1 in deliverables.md). Raising `max_workers` is the upgrade path, once sessions no longer share global state.
5. **Approval replaces `input()`.** *(edited)* Spending money takes two calls:
   - Creating the draft run returns one cost estimate for generation plus scoring, and stores it on the run.
   - `POST /runs/{id}/start` starts the job. That call is the approval.
6. **JSON shape.** Response models are Pydantic models with camelCase aliases, so field names match the frontend fixtures. Score data is serialized with `df.to_json(orient="records")`, so failed scores (`NaN`) arrive as `null`. They never go through `clean_score`, which turns `NaN` into 0.
7. **Doc IDs are always strings.** At upload, the chosen ID column is converted to `str`. If the user picks no ID column, the backend adds a `lloom_id` column (`"0"`, `"1"`, …) itself and passes it as `id_col`. This avoids C4 and the `"id"` overwrite.
8. **API key and models.** *(edited)* The settings page saves a provider, a model and an API key (`PUT /settings/models`), and these take priority. The model dropdown defaults to **"LLooM default"**, which is the notebook's mix (`gpt-4o` for synthesis, `gpt-4o-mini` for distill and score). A specific model is used for distill, synthesize and score, the same way `LLM_MODEL` works. Embedding always stays `text-embedding-3-large`. The UI supports OpenAI only. `.env` (`OPENAI_API_KEY` or `LLM_*`) is a fallback for developers, and the only way to use a local model. The key is stored in the local SQLite file and is never returned or logged.
9. **Testing.** Tests use FastAPI's `TestClient`, a temporary data directory and a fake model.
   - The fake model is a `Model` whose `fn` returns canned replies, the same approach the existing tests in `text_lloom/tests` take.
   - The app gets its models from one dependency, `get_models()`, which tests override.
   - No test needs an API key.

## 3. API surface

| Method & path | Purpose | Frontend screen |
|---|---|---|
| `GET /health` | Liveness check | — |
| `GET /projects` | Recent projects, newest `lastOpened` first | Home |
| `POST /projects` | Multipart upload: `name`, `description`, `files[]` | Create project |
| `GET /projects/{id}` | Project + its datasets (`DatasetFixture`) + its runs (`RunFixture`); updates `lastOpened` | Project overview, configure run |
| `GET /settings/models` | `{ provider, model, hasKey }`, from saved settings or `.env` (never the key) | Model settings, review run, progress |
| `PUT /settings/models` | Save `{ provider, model, apiKey }`; a blank key keeps the stored one | Model settings ("Save Settings") |
| `POST /settings/models/test` | One tiny LLM call → `{ ok, error }` | Model settings |
| `POST /projects/{id}/runs` | Create a `Draft` run from a `RunConfiguration` (+ optional `name`); the run includes `estimatedCost` | Review run |
| `PATCH /runs/{id}` | Replace a draft's configuration and recompute `estimatedCost` | Review run ("Edit configuration") |
| `GET /runs/{id}` | Run config, status, `estimatedCost`, model used, and `latestJob` | Review run, progress, results |
| `POST /runs/{id}/start` | Start (or retry) the run job: generate, then score → `{ jobId }` | Review run ("Start Run"), progress ("Retry") |
| `POST /runs/{id}/cancel` | Cancel a pending or running run | Progress ("Cancel Run") |
| `GET /jobs/{id}` | `{ id, status, step, done, total, error }` (same object as `latestJob`) | Progress |
| `GET /runs/{id}/results` | `RunResults`: concepts, documents (+ `metadata`), scores (`null` = failed), groupings | Concept explorer, concept details, document details |
| `GET /runs/{id}/export?format=csv\|json` | Download `export_df()` / `export_json()` (low priority) | — (no button yet) |

*(edited)* The concept endpoints (B8) and the separate score endpoints (B9) are no longer in the table, and neither is `/matrix`.

Run status moves through these states:

`Draft → Pending → Running → Completed`

A run can also end `Failed` or `Cancelled`. Either one can be started again, which reuses the draft's configuration.

FastAPI publishes the full schema at `/docs` (OpenAPI). D1.2 should build against that, not this table.

**B6. Job runner** *(edited)*
- `app/jobs.py`:
  - a single-worker `ThreadPoolExecutor`;
  - `submit(run_id, fn)`, which inserts a `jobs` row and runs `asyncio.run(fn(session, progress))` in the worker;
  - a progress callback (A4) that writes `step / done / total` to the row. `step` is stored as the progress page's stage name (`Distill`, `Cluster`, `Synthesize`, `Score`), using B7's mapping, so the frontend doesn't need to know LLooM's internal step names.
- The job object returned by the API is `{ id, status, step, done, total, error }`. `status` uses the run words, and `error` is the message of a `Failed` job, otherwise `null`.
- The session helpers `load_session(run_id)` and `save_session(run_id, sess)` live here:
  - loading unpickles the BLOB and attaches fresh models;
  - saving writes `get_pkl_str()` to the BLOB, and only runs after a job succeeds.
- Status updates:
  - **Submit:** the run is set to `Pending`.
  - **Worker picks the job up:** the run is set to `Running`.
  - **Success:** the run is set to `Completed`.
  - **Error:** the run and job are marked `Failed`, with the error message stored. The saved session is untouched.
- `GET /jobs/{id}`. On startup, any job still running, and its run, is marked `Failed` with the message "server restarted".
- **Cancel:** `POST /runs/{id}/cancel` sets `jobs.cancel_requested`.

  - The job and run end `Cancelled`, and the saved session is untouched.
  - A job still `Pending` is cancelled straight away and never runs.

**B7. Run: generate, then score** *(edited)*
- `POST /runs/{id}/start` accepts a `Draft`, `Failed` or `Cancelled` run. The progress page's **Retry** button (agreed with D1.2) calls it on a `Failed` run. Retry **restarts the whole run** from Distill: the session is only saved after a run succeeds, so a failed run has no partial state to resume. Starting is the cost approval, because the review page shows the estimate before "Start Run". The endpoint submits one job:
  1. `sess.gen(seed=..., params=..., n_synth=..., auto_review=..., debug=False, progress=...)`;
  2. then `sess.score(score_all=True, debug=False, progress=...)`, which scores every generated concept.
- Report progress using the progress page's four stages:

  | Step name the A4 callback reports | Stage shown on the page |
  |---|---|
  | `Distill-filter`, `Distill-summarize` | Distill |
  | `Cluster` | Cluster |
  | `Synthesize`, `Review` | Synthesize |
  | scoring | Score |

  B6's progress callback applies this mapping. Round numbers aren't reported: A4's callback doesn't pass them, and the progress page doesn't show them.
- On success, save the session once. The run ends `Completed`, and its `concepts` count is the number of active concepts.
- **Depends on B4.** Tests use B4's `fake_run` fixture; don't write new fake replies.
- Test: with `fake_run`, a run on a sample dataset ends `Completed`, with at least one concept and scores for every concept.

**B10. Results and export** *(edited)*
- `GET /runs/{id}/results` returns the `RunResults` shape that the results and concept details pages use (`lloom_web/src/fixtures/run-results.ts`):
  - `projectId`, `runId`, `datasetId`, `textColumn`, and `matchThreshold: 1`.
  - `concepts`, from the active concepts:
    - `id`, `name`;
    - `description`: `concept.summary`, or `""` when scoring found no matches, because `summarize_concept` only sets a summary when there is at least one;
    - `inclusionCriteria`: `prompt`;
    - `exampleDocumentIds`: `example_ids`, as strings.
  - `documents`: one per row of the dataset, `{ id, text, metadata }`. `metadata` holds every other column, with `NaN` sent as `null`.
  - `scores`: from `sess.get_score_df()`:
    - `conceptId`, `documentId`, `score`, `rationale`;
    - `evidence`: `[highlight]`, or `[]` when there is no highlight;
    - a failed score is `null`, never `0`. Build these from the raw score df, not through `clean_score`.
  - `groupings`: one per eligible dataset column, for the matrix's "Group by dataset column" dropdown. The frontend only counts documents into the slices it receives (`ConceptMatrix.tsx:22`), so the backend has to build them:
    - reuse LLooM's `get_groupings` (`concept_induction.py:1284`) for each column, with `max_slice_bins=5`;
    - a column is eligible if it is neither the text column nor the ID column, and it is either **numeric** or has **≤ 10 distinct values**. Free-text columns would otherwise produce one slice per row;
    - convert the result into the `DatasetSlice` shape (`run-results.ts`). Numeric bins (`pd.Interval`) become `{ kind: "numeric", columnId, lowerExclusive: left, upperInclusive: right, label: "(left, right]" }`. Category values become `{ kind: "category", columnId, value }`. Missing values become `{ kind: "missing", columnId }`.
- Before anything is scored, `get_score_df()` raises (`pd.concat([])` on an empty list), so return empty `scores` when `sess.results` is empty.
- **No `/matrix` endpoint.** The frontend computes the matrix counts itself from `RunResults`, so `vis_data()` isn't needed here.
- `GET /runs/{id}/export?format=csv|json` returns `export_df()` as CSV, or `export_json()`, as a file download. **Low priority:** no page has an export button yet. Note that `export_df` still turns failed scores into 0 (`develop-review-fixes.md` §2).
- **Depends on B4, not B7.** Tests load B4's `scored_session` into a run directly, so this commit can be built in parallel with B7.
- Test:
  - the failed score in `scored_session` shows up as `"score": null` in `/results`, never as `0`;
  - a dataset column that isn't the text column or the ID column appears in `documents[].metadata`;
  - a numeric column gets a grouping with at most 5 `numeric` slices, a column with ≤ 10 distinct values gets one `category` slice per value, and the text column gets no grouping;
  - the export CSV has the columns `export_df` documents.

> **Changed:** `/results` returns the frontend's `RunResults` shape instead of the flat score table, `/matrix` is dropped, and export is low priority.
> **Added:** `documents` with `metadata`, `groupings` built from LLooM's `get_groupings` for the matrix, the concept `description` taken from `summary`, and tests on B4's `scored_session`, so this commit no longer waits for B7.

## 5. Out of scope / for the team to decide

- **ZIP upload.** The frontend accepts `.zip`, but it isn't clear what a ZIP means: several CSVs, or one doc per text file? The backend returns 415 until D1.2 and D1.1 agree on that.
- **API key from the UI.** *(edited)* Decided: the page saves settings through `PUT /settings/models` (B4). The model dropdown's first option is "LLooM default (recommended)", which is the notebook's mix. Any other model applies to distill, synthesize and score, and embedding stays `text-embedding-3-large`. Picking `gpt-4o` raises the cost of a run by roughly 15×, because distill and score make most of the calls.
- **Local models in the UI.** *(edited)* Not in this version. Developers can still use one through `LLM_*` in `.env`. Adding it to the UI later means an "OpenAI-compatible" provider option with base URL, embedding model and context window fields on the settings page, and `PUT` accepting those fields and passing them to `build_models`.
- **Buttons with no designed page.** *(edited)* For the minimum complete version, these get **no backend work**. The frontend leaves them as they are (disabled or "not implemented"), and each one is a small commit later if time permits:
  - Add Dataset: `POST /projects/{id}/datasets`, reusing B3's upload parsing;
  - Project Settings: `PATCH` / `DELETE /projects/{id}`;
  - Run Settings: needs nothing new, since it can read `GET /runs/{id}`;
  - Open project, Import project, Search: undefined; search can filter `GET /projects` on the client;
  - Account Settings, Sign In/Out: out of scope, because the app is local-only with no auth;
  - Document Details and Outlier Details: need nothing new, since `/results` already carries the text, rationale, evidence and metadata.
- **Concurrency.** One job at a time (decision 4). Revisit if open question 1 says multi-user.
- **Left out because the spec and the UI don't need them yet:**
  - deleting projects or concepts;
  - concept selection and editing (B8, deferred);
  - auto-select (`select_auto`);
  - an upload size limit.

  Each is a small addition later.
- **Generate-then-select flow (flow (b)).** *(edited)* D1 scores every generated concept in one run, which matches the frontend. Pausing so the user can pick concepts before scoring would bring back B8 and B9, and the frontend would need a selection page.
- **Custom prompts / advanced params.** `gen(custom_prompts=...)` and manual `params` aren't exposed. The model settings "Advanced" tab is empty, so there is no UI for them yet.
- **Slicing the matrix.** *(edited)* Decided: the backend builds `groupings` with LLooM's `get_groupings` (B10), and the frontend counts documents into those slices. Manual bin edges (`slice_bounds`) aren't exposed.
- **`lloom.submit()`.** The backend never calls it. Whether to remove it is open question 5.
- **Caching, batching defaults and accurate estimates** belong to D3. **Validators and recorded replies** belong to D2. The backend calls both once they land.
